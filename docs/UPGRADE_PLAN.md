### 1.2 数据表实况

| 表 | 主键 | 关键约束 | 组织维度 |
|---|---|---|---|
| `teams` | `id` CHAR(24) | `team_id` 唯一（邀请码） | 自身 |

## 3. 关键偏差与修正

### 3.1 第四章「大模型调用彻底清除」不适用（最重要）

**事实**：当前项目是一个纯确定性系统。全仓检索确认无模型 SDK、无密钥、无 Prompt、无 AI 入口、无相关表（依据见 §1.3）。

**后果**：任务书 P0 的 13 项任务中，有 6 项（清理模型 SDK、删除模型配置密钥、删除 Prompt、删除 AI 前端入口、删除模型分析 API、清理模型依赖）**没有对象可执行**；第四章的 10 条清理验收也无法产出有意义的《清理验收报告》。

**修正**：

1. 删除独立清理阶段，P0 只保留「系统审计 + 建立基线测试」。
2. 把"不用大模型"从一次性任务转为**架构约束**，写入 `CODEBUDDY.md`：

   > 数据分析一律用确定性程序实现。禁止引入任何大模型 SDK、模型 API 调用、Prompt 工程或对话式问答能力。Agent 模块不得 import 任何网络模型客户端。

3. 保留任务书第四章的**精神**：新增代码不得以"AI 分析"为名引入外部推理服务。这类约束对后续协作者（包括 AI 编程工具）有实际价值。

### 3.2 API 命名风格：沿用 camelCase，不用点号命名空间

任务书 §13.2 使用 `tenants.create` / `agent_analysis.create_task` 这类点号风格，与现状 `createTeam` / `saveEntry` 不一致，且任务书自己也要求"与现有接口风格统一"。

**决定**：沿用现有扁平 camelCase，用**动词前缀**表达模块归属，不做双层分发。

| 任务书写法 | 本项目采用 | 说明 |
|---|---|---|
| `tenants.create` | `createWorkspace` | 与 `createTeam` 同构 |
| `tenants.list` | `listWorkspaces` | |
| `departments.create` | `createDepartment` | |
| `report_tasks.create` | `createReportTask` | |
| `analytics.overview` | `getAnalyticsOverview` | 与 `getTeam` 同构 |
| `agent_analysis.execute` | `runAnalysis` | |
| `agent_analysis.findings` | `listAnalysisFindings` | |
| `exports.create` | `createExport` | |

**理由**：`POST /api` 单入口 + `action` 字段分发是既有契约，`test_contract.py` 已按 22 个 action 做双向校验。改成 `a.b` 需要拆分分发器、改前端 `store.js` 全部调用点、重写契约测试，收益仅为命名美观，不符合"不重复建设、优先原文件修改"的约束。

### 3.3 Web 管理后台登录：小程序码扫码 + 轮询（已定）

任务书要求建设 Web 后台（§7），但未说明**浏览器环境下如何登录**。现状 JWT 只能由小程序内的 `wx.login` 换取，浏览器没有这个能力。

**已确认的产品约束**：

- Web 后台采用**扫码登录**。
- 只有**团队创建者**（`teams.owner_uid` 对应的人）可以登录 Web 后台，普通成员只能用小程序填报。
- 一人可属于多个工作空间，因此登录后需**选择以哪个创建者身份进入**管理端。

**两种扫码实现对比**：

| 方案 | 前提 | 身份打通 | 缺点 |
|---|---|---|---|
| A. 微信开放平台「网站应用」OAuth | 开放平台账号 + 网站应用审核（企业资质，约 1–7 天） | **需 unionid 映射**：网站应用 openid 与小程序 openid 不同，同主体同开放平台下 unionid 相同 | 现有 `members.user_id` 存的是小程序 openid，需引入 unionid 并回填历史数据 |
| B. **小程序码 + 轮询**（推荐） | 仅需已上线的小程序（已具备） | 直接复用小程序 openid，**身份天然一致，无 unionid 问题** | 需要轮询；小程序需增加一个"确认登录"逻辑 |

**决定：采用方案 B**。理由是它规避了本轮升级中最麻烦的一件事——unionid 映射与历史数据回填；同时不需要企业资质审核，可立即实施。

**登录流程**：

```text
Web 打开登录页
   │  POST /api  action=createLoginTicket
   ▼
后端生成 ticket（随机、5 分钟有效、一次性）
   │  调 wxacode.getUnlimited，scene=ticket
   ▼
返回小程序码 → Web 展示并开始轮询
   │
   │ 用户用微信扫码 → 打开小程序"确认登录"页
   ▼
小程序 POST /api  action=confirmWebLogin{ticket}（带小程序 JWT）
   │
   ├─ 校验：该 openid 是否为任一 team 的 owner_uid
   │     ├─ 否 → 拒绝，提示"仅团队创建者可使用管理后台"
   │     └─ 是 → 列出其创建者身份的工作空间
   ▼
Web 轮询 action=checkLoginTicket{ticket}
   │
   └─ 已确认 → 返回 Web 专用 JWT（12 小时）+ 可管理空间列表
```

**token 隔离**：Web 端签发独立 claim（`aud: web`，12 小时），与小程序 30 天 token 互不通用；新增 `refreshToken` action 仅对 `aud=web` 生效。服务端校验时按 `aud` 区分可用接口集合，Web token 不得调用填报类 action。

**需要新增**：`web_login_tickets` 表（见 §6.1）、`createLoginTicket` / `confirmWebLogin` / `checkLoginTicket` / `refreshToken` 四个 action、小程序"确认登录"页。

### 3.4 定时任务并发安全（任务书空白，高风险）

任务书 §14.1 提出"在 FastAPI 现有服务体系内做后台任务"，但未考虑部署形态。

**风险**：当前生产配置是 `gunicorn -w 2`（2 个 worker 进程）。若在应用内启动定时器（APScheduler 等），**两个 worker 会各跑一次**，导致同一周期分析重复执行、报告重复生成、异常记录重复写入。

**三个可选解法**：

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 调度 + 幂等键 | APScheduler 在每个 worker 启动，但执行前抢数据库唯一键 | 改动最小；推荐 |
| B. 独立调度容器 | docker-compose 增加 `scheduler` 服务，单进程运行，`-w 1` | 隔离最彻底，运维成本 +1 容器 |
| C. 外部 cron 调接口 | 宿主机 crontab 调受保护接口 | 简单，但接口需内网鉴权 |

**建议 A**，并强制要求幂等唯一键：

```sql
UNIQUE KEY `uk_analysis_idem` (
  `workspace_id`, `analysis_type`, `period_start`, `period_end`, `rule_version`
)
```

抢键失败即视为"已执行过"，直接返回既有结果。这也是任务书 §9 要求的"重复任务不产生重复结果"的唯一可靠实现方式。

### 3.5 模板快照：任务书要求现状已满足，无需加表

任务书 §6.3 要求"历史日报必须使用原始提交时的模板版本快照还原，不能因模板修改导致字段错位"。

**实测结论**：现状已满足，且**不需要新增快照字段或快照表**：

1. `daily_entries` 存 `template_id` + `template_version`（`schema.sql:65-66`）。
2. 已发布模板**不可编辑**：`update_template_row` 对 `published` 状态直接拒绝（`templates.py:101-103`）。
3. 已发布模板**不可删除**：`delete_template_row` 对 `published` 状态直接拒绝（`templates.py:115-117`）。
4. 发布新版本时，旧版本仅置为 `archived`，**行保留**（`templates.py:186-194`）。

因此每条历史日报都能精确回指到不可变的历史模板版本行，字段不会错位。

**需要补的不是功能，而是保护**：

- 新增测试：断言「已发布/已归档模板行不可删、不可改字段」。
- 新增约束说明到 `docs/DEVELOPMENT.md`：任何数据迁移脚本禁止物理删除 `form_templates` 中 `published`/`archived` 的行。

> 这一结论省掉一张快照表和一次历史数据回填迁移，是本轮对比中收益最大的一条。

### 3.6 「应提交人数」口径必须升级（任务书判断正确）

任务书 §7.4 指出应提交人数不能简单用模板下发范围并集计算。**现状确实如此**：当前看板按"全部已生效模板 scope 的并集"取名单，未考虑：

- 成员 `status = disabled` 应排除
- 成员加入/离开团队的时间区间
- 工作日规则（周末是否填报）
- 任务截止时间前后的状态差异
- 免填/请假记录

**修正**：`report_tasks` 表为单一事实来源，新增 `compute_expected_submitters(workspace, task)` 计算函数，看板、报表、Agent 三处**共用同一函数**，不得各自实现。这是任务书 §18.2「唯一业务链路」在核算口径上的具体落点。

## 4. 不变约束（红线）

以下为硬约束，任何阶段不得违反：

1. 不重建 `daily_entries`，不改 `form_data` 结构，不迁移历史日报。
2. 不物理删除 `form_templates` 中 `published` / `archived` 行。
3. 不改变现有 22 个 action 的业务语义（可新增，不可静默改义）。
4. 权限判断只在服务端；前端隐藏按钮不构成权限控制。
5. Agent 只读业务数据，不得写 `daily_entries` / `form_templates` / `members`。
6. 不引入任何大模型依赖（见 §3.1）。
7. 指标计算只允许一份实现，禁止在看板、报表、导出中各写一套。
8. 分析结果必须可追溯（数据范围 + 指标版本 + 规则版本 + 执行时间）。
9. 不新建平行日报系统、平行模板系统、平行权限体系。
10. 新增 action 必须同步：`store.js` + 服务端 handler 注册 + `test_contract.py` 契约用例。

        │
   ┌────┴──────────────┬──────────────────┬────────────────┐

 身份与组织          模板与任务          数据服务        分析服务
 auth / workspace    templates /        entries /       metrics /

   │                   │                  │                │
   └────┬──────────────┴──────────────────┴────────────────┘
        │

        │

## 6. 数据模型增补（收敛后 12 张）

### 6.1 必须新增（按阶段）

| 表 | 阶段 | 用途 | 关键约束 |

| `workspaces` | P4 | 工作空间（租户边界） | `workspace_id` 唯一 |

## 7. 阶段计划（重排后 7 阶段）

### 调整说明

任务书顺序为 P0 审计 → P1 填报 → P2 模板任务 → P3 组织 → P4 Web → P5 Agent → P6 通知 → P7 验收。

**两处重排**：

1. **Agent 从 P5 提前到 P3**。理由：分析能力是本产品的差异化核心，且它只依赖"日报 + 模板字段"这两个已存在的东西，**不依赖多工作空间**。可以先在单团队模型上（`workspace_id` 暂填 `team_id`）跑通指标与规则，最早验证核心价值。若放在多租户改造之后，会拖到项目后期才能验证方向是否正确。
2. **组织与 Web 后移**。理由：多租户改造会牵动全部 5 张表的唯一键与索引，越晚做返工越少；Web 后台是投入最大的单项工程，应在数据模型稳定后再动工。

## 8. 首批指标与规则（MVP 范围）

### 8.1 指标（6 个）

| metric_code | 名称 | 口径 | 边界 |
|---|---|---|---|
| `SUBMIT_RATE` | 提交率 | 已提交人数 / 应提交人数 | 分母为 0 → 不计算，返回 `null` |
| `SUBMIT_COUNT` | 已提交人数 | 当日 `status='submitted'` 的去重人数 | 排除 `disabled` 与未加入成员 |
| `EXPECTED_COUNT` | 应提交人数 | `compute_expected_submitters` 结果 | 单一实现（§3.6） |
| `FIELD_SUM` | 数值字段合计 | 按模板 `statType='sum'` 的字段求和 | 跳过缺失值，不补零 |
| `FIELD_AVG` | 数值字段均值 | 求和 / 有效样本数 | 样本 0 → 不计算 |
| `PERIOD_GROWTH` | 周期增长率 | (本期 - 上期) / 上期 | 上期为 0 → 不计算；周期不完整 → 标记 `incomplete` |

### 8.2 规则（3 条）

| rule_code | 条件 | 输出 | 等级 |
|---|---|---|---|
| `SUBMISSION_RATE_LOW_01` | 当日提交率 < 80% | 提醒团队负责人 | warning |
| `METRIC_DROP_01` | 本期指标 < 上期 × 80% | 生成异常记录 | warning |
| `MISSING_DATA_01` | 指定周期内应提交但无记录 | 生成数据缺失异常 | info |

> 阈值全部可配置，不硬编码。首批只做这 3 条，验证引擎正确后再扩充（任务书 §11 的示例规则作为二期候选）。

### 8.3 报告生成规则

- 只用结构化指标 + 规则触发记录拼接文本，不生成任何未在数据中出现的描述。
- 每份报告必须带：`workspace_id`、`analysis_type`、`period_start/end`、`data_snapshot_time`、`metric_version`、`rule_version`、`execution_id`。
- 数据不足时输出"数据不足，暂不生成结论"，不得补充推测。

### 8.4 横向对比范围（角色驱动，已定）

已确认：分析支持团队横向对比，可对比范围由**查看者的角色层级**决定。

| 角色 | 可对比范围 |
|---|---|
| 工作空间所有者 | 本工作空间内全部部门与团队 |
| 工作空间管理员 | 授权范围内的部门与团队 |
| 部门负责人 | 本部门及其下级团队（≤3 级） |
| 团队负责人 | 仅本团队，不提供横向对比 |
| 普通成员 / 只读成员 | 不提供分析入口 |

实现要求：

1. 对比范围由服务端依据 `members.role` + 部门树计算，**前端传入的 `teamIds` 仅作筛选条件，不能作为授权依据**。
2. `analysis_tasks.scope` 记录本次实际计算范围，`analysis_results` 一并保存，便于追溯"当时对比了哪些团队"。
3. 可对比团队数 < 2 时，返回"范围不足，无法横向对比"，不生成排名。
4. 排名并列规则统一：按主指标降序，主指标相同则按次指标降序，仍相同则并列（不强行分出名次）。
